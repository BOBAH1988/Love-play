# Бэкенд «Давай играй»

Свой сервер для того, что сейчас держится на Firebase: аккаунты и вход,
уровни доступа, реестр игр, личное состояние, статистика, админ-панель.

Принцип: **ничего не коммитится в Firebase, пока не готово.** Ветка `backend`
работает у вас на машине и на вашем сервере; приложение на GitHub Pages остаётся
на Firebase, пока вы не переключите `backend-config.js`.

> Убедиться, что приложение не сломалось, можно в любой момент:
> `node tools/check.js` и `node tools/smoke-test.js` в корне проекта —
> они проходят и при режиме `firebase` (по умолчанию).

---

## 1. Что внутри

| Файл | Назначение |
|---|---|
| `server/src/index.js` | HTTP-сервер: `/api/*` и статика приложения с того же домена |
| `server/src/routes.js` | все маршруты API и проверка прав |
| `server/src/store.js` | все запросы к базе в одном месте |
| `server/src/model.js` | перевод документов Firestore ↔ строки базы, слияние `gameStats` |
| `server/src/auth.js` | пароли (scrypt), токены сессий |
| `server/src/mailer.js` | письма: сброс пароля, приглашение установить пароль |
| `server/src/migrate.js` | перенос из Firebase в свою базу |
| `server/src/verify.js` | сверка содержимого после переноса |
| `server/migrations/001_init.sql` | схема базы |

Зависимостей нет: только Node 22.5+ и встроенный `node:sqlite`.
Это сознательно — на своём сервере меньше того, что надо обновлять и что может сломаться.

## 2. Режимы перехода

`backend-config.js` в корне проекта:

```js
window.COP_BACKEND = {
  mode: 'firebase', // firebase | dual | server
  baseUrl: '',      // '' — API на своём же домене
};
```

| Режим | Чтение | Запись | Когда |
|---|---|---|---|
| `firebase` | Firebase | Firebase | сейчас; ничего не меняется |
| `dual` | Firebase | Firebase **и** сервер | первая неделя после запуска сервера |
| `server` | сервер | сервер | после успешной сверки |

Режим можно переключить в браузере без правки файла:
`localStorage.setItem('cop-backend-mode','server')` и перезагрузка.
Это удобно для проверки, но на устройстве пользователя режим из файла
перекрывает локальное значение при загрузке.

## 3. Запуск на машине разработчика

```bash
cd server
node src/index.js
# http://127.0.0.1:8080 — приложение, /api/health — проверка
```

По умолчанию письма не отправляются, а печатаются в консоль
(`[mail:dry-run] ... token=...`) — ссылку из письма можно открыть вручную.

Тесты:

```bash
cd server
npm test          # 16 сценариев: вход, права, слияние статистики, сброс пароля…
```

## 4. Настройки сервера

Переменные окружения (файл `server/deploy/come-on-play.env`, права 600):

| Переменная | Обязательна | Что значит |
|---|---|---|
| `PUBLIC_URL` | да | `https://ваш-домен` — для ссылок в письмах |
| `DB_FILE` | нет | путь к базе, по умолчанию `server/data/come-on-play.db` |
| `ADMIN_EMAILS` | да | список админов через запятую (сейчас — `79042044926@ya.ru`) |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM` | для писем | без них ссылки печатаются в лог |
| `COOKIE_SECURE=0` | только локально | без HTTPS cookie не ставятся |
| `FIREBASE_PROJECT_ID`, `FIREBASE_API_KEY` | для переноса | если не заданы, берутся из `firebase-config.js` |
| `PORT`, `HOST` | нет | по умолчанию `8080` / `127.0.0.1` (за Caddy) |

Секретов в репозитории нет и быть не должно: `server/.gitignore` исключает
`.env`, `*.db`, `data/`.

## 5. Развёртывание

Полный порядок — в [deploy/README.md](deploy/README.md): Caddy, systemd,
бэкапы, проверка. Коротко:

```bash
cd server/deploy
sudo cp come-on-play.service /etc/systemd/system/
sudo cp come-on-play.env.example /etc/come-on-play.env   # заполнить и chmod 600
sudo systemctl daemon-reload && sudo systemctl enable --now come-on-play
```

## 6. Перенос данных

**Сначала копия.** В консоли Firebase: Firestore → Экспорт в JSON / бэкап.
Это единственная копия, не зависящая ни от одного сервиса.

Затем на сервере (или локально, если база потом переедет):

```bash
cd server
node src/migrate.js --dry-run          # отчёт без записи
node src/migrate.js                    # запись
node src/verify.js                     # сверка содержимого
```

Если REST API Firestore отвечает 403 (правила закрыты), выгрузите базу
в JSON и запустите `node src/migrate.js --file выгрузка.json`.

Что важно знать до запуска:

- **Пароли не переносятся.** Firebase не отдаёт хэши. Перенесённый пользователь
  получает `legacy_auth = 1`: при попытке входа сервер отправляет письмо
  «установите новый пароль». Письма требуют SMTP — без него люди не смогут войти.
- **`gameStats` сливается**, а не перезаписывается: иначе поздние записи затрут
  ранние. Это проверено тестом `слияние статистики не затирает ранние счётчики`.
- **Пользователь без почты не переносится** — без неё невозможен вход. Список
  таких документов печатается в отчёте.
- **Заявки на доступ** переносятся, но правило «писать может любой
  авторизованный» больше не действует: на сервере одна почта — не больше
  трёх заявок в сутки.

## 7. Что изменилось в клиенте

- `api.js` — адаптер. В режиме `firebase` возвращает `null` из `currentSession()`,
  и клиент работает с Firebase как раньше.
- `core.js` — `openAccount()` сначала спрашивает адаптер. Серверный режим
  показывает профиль и уровень из `/api/me`; синхронизация состояния идёт
  через `/api/me/state` в обоих режимах чтения.
- `fants-timer.js` — статистика (`gameStats`) и смена уровня в админ-панели
  уходят на сервер, когда он включён.
- Уровень доступа при `server` берётся из сессии сервера, а не из
  `window.__userAccessLevel`, который можно подменить в консоли.

## 8. Чек-лист переключения

1. `node src/migrate.js` и `node src/verify.js` — «Расхождений нет».
2. `backend-config.js`: `mode: 'dual'`. Неделя наблюдения, сравнение
   `/api/admin/general` и Firebase.
3. `mode: 'server'` на своём домене (приложение и API — один origin).
4. Проверить вход, профиль, смену уровня, статистику, «Выйти».
5. Переключить DNS приложения на сервер, если раньше оно жило на GitHub Pages.
6. Через 7 дней без ошибок — убрать теги `gstatic.com` из `index.html`
   и удалить `firebase-config.js` из статики.
7. Только после этого — удалять проект Firebase.

Откат в любой момент до шага 6 — правка `mode` в `backend-config.js`.
